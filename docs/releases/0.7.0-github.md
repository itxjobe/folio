# GitHub setup for 0.7.0

> **The branch stays local until the beta ships** (McCal, 2026-09-18). `release/0.7.0` isn't pushed, the Market is
> hidden behind `MarketFeature` (Folio Dev, Beta Updates, or a supporter code), and `folio-packages` is public but
> publishes nothing until its key exists. Everything below is what happens *when* that changes.

The Market turns Folio from one app into something people publish to, so GitHub stops being just where the code lives.
Nothing here is done yet, and nothing is pushed or created without McCal saying so. Roughly in order of what matters.

## 1. Before the Market ships (needed)

- [x] **`folio-packages` repo** — https://github.com/McCal-Codes/folio-packages (public, 2026-09-18). Anyone opens a
      pull request to list a package. It has `CONTRIBUTING.md` (what gets accepted, how an update is reviewed, how a
      takedown works), a `template/hello-tweak` to copy, `tools/build.py` (packs each folder, pins it with a sha256,
      copies pictures out to the site, signs the index) and an Action that validates against `docs/sdk/schema/v1/` and
      deploys to Pages. Signing only ever runs on `main`, so a pull request can't reach the key.
      Still to do, and only McCal can: **generate the key** (`bash tools/keygen.sh`, then
      `gh secret set FOLIO_SIGNING_KEY < folio-source.pem`), **turn Pages on** (Settings → Pages → Source: GitHub
      Actions), and afterwards add `https://mccal-codes.github.io/folio-packages/` in the app as a source. Until the
      key exists the Action says so and publishes nothing, because Folio refuses an unsigned source.
      Not there yet: issue forms for **Submit a package**, **Report a package** and **Takedown**, and running the
      Mockup Lab checks on a submitted package.
- [ ] **`folio-source-template` repo.** "Use this template" → add package folders → a GitHub Action validates, packs,
      builds and signs the index, and publishes to Pages. Its README takes an author from nothing to a `folio://source/`
      link.
- [ ] **The signing key lives in one place.** A repository **environment** (say `publish`) holds it, with required
      reviewers so a workflow can't sign on its own. Never in the repo, never in a plain secret used by every workflow.
- [ ] **Pages for `folio.mccal.dev`.** The schemas are already published under that name
      (`https://folio.mccal.dev/schema/v1/…`), so the URL has to resolve before authors rely on editor autocomplete.
      The Folio source (`docs/sdk/source/`) can be served from the same place.
- [ ] **Revocation before the first community package.** `revoked.json` is signed and the process is written down:
      who can revoke, how fast, and what the user sees.

## 2. Release trust (what McCal asked about)

- [ ] **Publish the APK's SHA-256** in the release notes, next to the download.
- [ ] **VirusTotal scan per release.** Upload the exact APK, wait for the report, and link it in the release notes and
      the README badge area. Two caveats worth knowing: an uploaded file is shared with VirusTotal's partners, and a
      sideloaded launcher with `REQUEST_INSTALL_PACKAGES` sometimes draws one or two heuristic flags from small engines.
      Linking the report with a line explaining any flag is better than hoping nobody scans it themselves.
- [ ] **[PERMISSIONS.md](../../PERMISSIONS.md)** stays current, linked from the README and from the release notes. A
      plain list of what each permission does is what actually calms people; the scan is the backup.
- [ ] **Build provenance.** `actions/attest-build-provenance` on the release APK proves it came from a tagged run of
      this repo. Combined with the checksum, someone can tell a real build from a re-packaged one.
- [ ] **Obtainium-friendly releases.** Keep one APK asset per release with a stable name, so Obtainium users can follow
      the repo directly. This is also how Folio itself appears in an `externalApp` listing later.

## 3. Repository hygiene (cheap, worth doing once)

- [ ] **Branch protection on `main`:** require the CI check, require a PR, no force pushes.
- [ ] **Tag protection** for `v*`, so a release tag can't be moved after the fact.
- [ ] **Secret scanning and push protection** on, for all three repos.
- [ ] **Dependabot** for GitHub Actions (the workflows pin SHAs, which is right; Dependabot keeps them fresh).
- [ ] **CODEOWNERS** so `docs/sdk/`, `market/` and the workflows need McCal's review.
- [ ] **Issue forms** in the main repo: bug (with device, screen, Folio version), feature idea, and "doesn't work on my
      fold" — the Z Fold 7 report showed how much that one matters.
- [ ] **A PR template** with the one line that counts: which lab checks were run.
- [ ] **`SECURITY.md`** already exists; add how to report a malicious package, and the revocation promise.

## 4. Later, not now

- Reusable workflows shared between the three repos, once they've diverged enough to be annoying.
- F-Droid metadata, which needs a reproducible build and is a project of its own.
- A GitHub App or bot for community PR triage. A human reading the first fifty PRs is better than automating early.

## Notes

- Everything CI signs is a static file. Folio never calls the GitHub API from the phone, which is what keeps it clear of
  the 60-requests-an-hour limit ([ADR 0001](../adr/0001-repo-format.md)).
- The three-repo split exists so a community package can never touch Folio's code, and so Folio's key never signs
  something a stranger wrote.
